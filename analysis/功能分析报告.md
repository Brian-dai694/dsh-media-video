## 结论摘要

四个输入并非四个同类剪辑器：

- **video-editor**：功能原型，提供视频合并、转码/尺寸处理、剪辑播放/帧预览，以及人脸检测/换脸相关页面或实验接口。README 明确称人脸替换 API 仍待实现，部分接口和 UI 的实际闭环需进一步核对。
- **OpenReel**：规模最大的完整创作套件，包含非线性视频编辑器、图片编辑器、桌面端、Web/云端服务、AI 工具代理、可扩展的效果/资产生态和创作者市场相关服务。静态扫描展示的源码覆盖不完整，以下功能摘要综合其文档和可见源码，不等同于实机验收。
- **ComeCut（来剪）**：面向用户的 Web/桌面视频编辑器，重点是 ASR 字幕、翻译、TTS 配音、视频合成、AI 助手、音频分离/还原、抠图和 GIF 导出。此 ZIP 以网站文档和构建后资源为主，不含完整的编辑器开发源码，因此不能逐功能从源码验证实现质量。
- **HunyuanVideo-1.5**：视频生成模型/推理与训练代码，不是时间线剪辑器。支持文生视频、参考图生视频、提示词改写、超分辨率、推理加速/卸载与训练/微调路径；模型权重需另行获取，当前机器上未验证推理。

**与当前目标工程的方向判断**：`dsh-media-video` 是 DSH 内嵌、基于轨道/剪辑/叠加层的可审计编辑器内核及宿主桥接，不是桌面级完整 NLE，也不是生成模型。最直接的功能参照是 OpenReel 的时间线/剪辑数据模型与 agent 工具闭环；ComeCut 可作为字幕翻译配音工作流参考；HunyuanVideo 可作为以后生成能力的独立后端接入对象；video-editor 的合并/转码/人脸处理则是独立媒体处理服务路线。

## 1. video-editor

### 可观察功能

- **视频导入与合并**：上传组件支持多视频文件，调用 `/api/video/merge`，服务端 `VideoController` 负责合并并返回视频 URL、文件名与总时长。
- **浏览器播放与帧预览**：编辑/处理页面使用 HTMLVideoElement 和 Canvas，按帧率计算缩略帧，支持播放定位及播放速度设置（部分速度控件行为需以源码实际调用为准）。
- **输出处理**：处理页向 `/api/video/process` 提交输出宽高等参数；转码抽屉向 `/api/video/trans` 提交视频路径和码率参数，并提供生成文件下载。具体编码参数映射、格式能力及失败处理需继续沿 controller/service 逐项核对。
- **人脸方向功能**：存在 `DetectPage`、face-api.js 依赖、人脸模型文件和 Haar cascade 资源；前端能够消费 detectionList 并展示检测结果。目录另有 `face.html` 及独立 `server/test.ts` 的 `/api/replace-face` 示例，后者用 FFmpeg overlay 合成上传视频和人脸图片。
- **辅助工作流**：包括拖拽组件、TransformDrawer、CodeMirror 多语言代码编辑器、用户操作记录 hook，以及用户/上传/图像相关服务模块。

### 关键限制/风险

- README 的服务器章节说明“人脸替换 API 待实现”；独立 `server/test.ts` 也只是 Express 示例代码，不能据此断言已接入 Midway 正式路由。
- 上传服务代码包含“另一个服务分析 video”的 TODO；因此不能把所有上传处理能力视为完备。
- 多份锁文件并存（npm/yarn），部署和依赖版本来源不唯一。
- 前端出现调用与服务端路径不代表具体转换算法、FFmpeg 安全性、并发/大文件处理或生产级错误恢复均已验证。

- `src/components/UploadView.tsx`、`src/components/TransformDrawer.tsx`、`src/components/CodeEditor.tsx`

- **创作工作室/效果资产**：studio 发布验证与提交模块；`fxpkg` 含节点/manifest 校验、拓扑排序、打包、校验和、签名载荷与尺寸限制。说明具备效果包/资产发布机制的静态实现基础。
- **图片编辑器**：`apps/image` 与 `packages/image-core` 包含图层/画板项目模型、选择/遮罩、颜色调整、滤镜/混合、矢量形状/钢笔路径、填充、吸附等实现模块；这是与视频剪辑并列的子应用。
- **云端/市场服务**：`apps/cloud` 可见 crash routes、marketplace 的身份认证、限流、存储、工作室事件、自动检查及制品构建；`packages/fxpkg` 还有收入分配/支付草稿等业务函数。代码/测试存在不等于云环境已经部署或商业流程正在生产运行。
- **桌面/Web 交付**：Electron desktop 配置、Web 构建、云 worker 配置与 CI/release 工作流存在。发布产物、签名、安装流程及实际平台兼容性未执行验收。
- **移动与离线**：仓库有 `MOBILE-OFFLINE.md`、`MOBILE-PARITY.md` 等文档，属于明确的设计/测试范围；本次没有针对移动真机或离线场景运行。

## 4. HunyuanVideo-1.5

### 可观察功能面

- **文生视频（T2V）与图生视频（I2V）**：`generate.py` 按 `--image_path` 选择任务，接收正向/负向 prompt，要求选择 480p/720p，并将视频写为 24fps 输出。
- **生成提示词处理**：支持 prompt rewrite 开关；模型代码含双语文本编码/ByT5 相关模块。
- **视频超分辨率**：默认可启用 SR 输出，文档描述增强至 1080p；同时支持保存超分辨率前视频。
- **推理优化**：CLI 支持 step distillation、cache、sparse attention、torch compile、offloading/group offloading 及 overlap 等参数；性能取决于具体 GPU、依赖、权重和参数，不能从选项存在推断速度保证。
- **训练/微调**：`train.py` 提供训练流程，源码/文档提及分布式、FSDP、context parallel、梯度检查点、Muon optimizer、验证视频；存在图像/视频数据路径、I2V 概率等训练控制。
- **生态接入**：仓库包含 ComfyUI 指南；README 声明 Diffusers/LightX2V 等社区集成。社区项目并非都包含在此 ZIP。

### 运行前提和限制

README_CN 的系统要求指出 Linux、Python 3.10+、CUDA 兼容的 NVIDIA GPU，最低显存 14GB（开启卸载的条件下）；所需权重需另行下载。当前 ZIP 里的模型相关图片资源有若干极小占位文件，不能把它们视作模型权重或有效演示素材。没有尝试装依赖或跑推理/训练。

## 面向本地工程的建议（基于本次证据）

1. **优先保持边界清晰**：现有轨道/状态/导出/宿主桥接作为剪辑核心；媒体生成、ASR/TTS/翻译和大型图像编辑应先以独立能力/provider 集成，而不是混入核心 reducer。
2. **参考 OpenReel 的可验证命令模型**：将每类操作明确成输入 schema、状态变更、风险等级、undo 与测试；现有 revision/digest/commandId 机制是合适的基础。开展对照时要再核对 OpenReel 的命令契约、权限确认和恢复策略具体实现。
3. **先补用户可见编辑闭环**：若目标是向完整剪辑器发展，按优先级验证并补齐媒体库/代理资源、字幕轨、音频分离、文本样式、轨道缩放与吸附、项目持久化、导出兼容性。每项应拆成独立可测功能，不把“功能全”当一次性大改。
4. **生成能力走异步任务适配器**：HunyuanVideo 需要 Linux/CUDA/额外权重，适合作为本地或远端 worker。宿主页面负责 prompt/参考图和 job 状态；媒体字节和模型运行留在 worker；成功后再导入生成视频素材。当前未设计或实现该连接。
5. **借鉴 ComeCut 译制链路但先核后接**：字幕识别、对齐、翻译、TTS、合成有多步失败点，应定义中间产物、语言/说话人/时间码契约和人工校对点；ComeCut 当前包的实现不可见，只能作产品流程参考。
6. **视频处理服务要独立审查安全边界**：video-editor 的文件上传和 FFmpeg 示例提示需要校验路径、命令参数、大小/时长上限、临时文件清理与并发限制，不能直接搬用实验 API。

以上是研究建议，不代表对代码作了改动或已验证任何上游产品在运行。
